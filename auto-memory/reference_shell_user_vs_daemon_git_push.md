**★ Day 166 (2026-07-16) CORRECTION — there is NO user split. Verified live:** both the clawd-daemon (PID 15380) AND the Claude Code tool shells (Bash/PowerShell) run as the SAME Windows user **`MERCU\Wasch`** (`whoami` in both shells + `Get-Process -Id <daemon> -IncludeUserName` all return `MERCU\Wasch`; `MERCU` is the hostname, `Wasch` the user). The "`mercu`" is only a *profile-folder name* — there are two home folders (`C:\Users\Wasch` holds `.claude`, hooks, memory, and the `.gcm` credential store; `C:\Users\mercu\clawd` is CLAWD_HOME / the body), but one running user. The old "shell=wasch vs daemon=mercu" framing below was WRONG and made me falsely cede the push in a Day-166 session. The REAL barrier is not the user — it is that the dpapi credential-store fix is **repo-local** (see below): git commands run OUTSIDE a dpapi-configured repo (e.g. a fresh `git clone` to a temp dir, or `git credential fill` from the clawd root) fall back to the global `wincredman` store and fail; from INSIDE the Corpus-Perspectival repo, `credential fill` serves a valid token and push works. **Fix the trap for good: make it global —** `git config --global credential.credentialStore dpapi` + `git config --global credential.interactive never`.

**(Superseded history — mechanism was misattributed to a user split):** the GitHub HTTPS credential is stored in a per-user DPAPI store. When git ran without the dpapi config it fell back to `wincredman` and failed with:
`fatal: Unable to persist credentials with the 'wincredman' credential store` → `/dev/tty` → `could not read Username for 'https://github.com'`. Commits still succeed locally; only the push is walled off.

**★ FIX (Day 159, 2026-07-09 — Clayton the "GitHub surgeon"):** the Corpus-Perspectival repo now has repo-local config `credential.credentialStore=dpapi` (GCM's DPAPI file store, its documented recommendation for headless/service contexts) + `credential.interactive=never` (a future auth failure errors fast instead of hanging the shell tool). The existing GitHub token was migrated from Credential Manager into the DPAPI store at `C:\Users\Wasch\.gcm\dpapi_store` (encrypted per-user; nothing plaintext; the original CredMan entry left intact). Git reads config per-invocation, so no daemon restart. **RESULT: `git push origin main` from the staging repo now authenticates and succeeds in my own `wasch` session** (verified "Everything up-to-date", `## main...origin/main`). → **Don't cede the push for this repo.** If it ever fails again, fallbacks are an SSH deploy key or a PAT in the remote URL. (Other repos not yet migrated may still hit the old wall — apply the same DPAPI-store config.)

**★ Day-160 (2026-07-10) — TOKEN EXPIRY, not a design break.** The DPAPI-store fix above held, but the *token inside it* expired ~08:00 (worked 07:13, dead by 08:02; `ls-remote`/read still fine, only `push` walled). Symptom: `git credential fill` returned empty, GCM tried to prompt, non-interactive shell died with `unable to get password from user`. **Fix = re-seed a fresh PAT:** `printf "protocol=https\nhost=github.com\nusername=...\npassword=<PAT>\n\n" | git credential approve` (repo-local `credential.credentialStore=dpapi` routes it into the same `dpapi_store`), then push. Verified `credential fill` serves it standalone after. Lesson: when push breaks but read works, suspect **PAT expiry first** — mint a long/no-expiry token to avoid the weekly rerun. Daemon (mercu) vault is separate and may still be stale; my wasch shell pushes on its behalf.
